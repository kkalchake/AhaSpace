Week 18 — Public demo mode

Browsing AhaSpace without an account: the public course demo

Before this week, every course route required a JWT — a visitor with no account had nothing to look at except a login form. This week adds a second, unauthenticated path through the same course data: one course (AI Engineering From Scratch) is flagged isPublic = true on the Course row, a brand-new set of /api/public/courses... endpoints serves only public courses with no JWT required, and the frontend's course pages fetch from those endpoints when nobody is logged in. The section-embedded AI chat panel still renders for a logged-out visitor — it just intercepts the send action client-side and asks them to sign in, without ever touching the network. Nothing about the existing authenticated /api/courses/** path changes except that its response body gained a few new fields. Every screenshot below is a real request against a real running backend and a real Postgres database — none of this is mocked.

Setup

Three things need to be running, in this order: Postgres (with the enlightenment database and ahaspace user this project's docker-compose.yml creates), the backend on two Spring profiles at once (dev for the Postgres datasource, seed for the one-time curriculum seed that now marks a course public), and the frontend dev server.

Start Postgres

The project's own docker-compose.yml (repo root) is the supported path — it creates the enlightenment database and the ahaspace user/password application-dev.yaml already expects, with no manual SQL needed:

cd AhaSpace
docker compose up -d
docker exec ahaspace-postgres pg_isready -U ahaspace -d enlightenment

Docker Desktop's daemon was not running in the environment this guide was built in, so a native Homebrew Postgres install was used instead, with the role and database created by hand to match the compose file exactly:

brew services start postgresql@14
psql -h localhost -p 5432 -d postgres -c "CREATE ROLE ahaspace WITH LOGIN PASSWORD 'ahaspace';"
psql -h localhost -p 5432 -d postgres -c "CREATE DATABASE enlightenment OWNER ahaspace;"

Either path ends at the same place: a Postgres server on localhost:5432 with a database named enlightenment owned by a user named ahaspace / password ahaspace. Use whichever is actually available.

Start the backend on dev,seed — this is the one new wrinkle this week

CurriculumSeedRunner is @Profile("seed") and reads @Value("${curriculum.source-path}") — that property has no default anywhere in application.yaml or application-dev.yaml, so it must be passed on the command line every time the seed profile is active. It points at a checkout of the actual upstream curriculum repo:

# if not already present at the repo root:
git clone https://github.com/rohitg00/ai-engineering-from-scratch.git

./mvnw spring-boot:run \
  -Dspring-boot.run.profiles=dev,seed \
  -Dspring-boot.run.arguments=--curriculum.source-path=/absolute/path/to/AhaSpace/ai-engineering-from-scratch

Wait for SERVER IS LIVE on http://localhost:8080!. Before that line, watch for this — it only prints once, on the run that actually creates the course row:

The seed is idempotent by design (findByTitle(...).orElseGet(...) in CurriculumSeedRunner, existsByTitle per phase in CurriculumPhaseSeeder) — running it again against an already-seeded database is a silent no-op, it does not duplicate rows or error.

If you'd rather not run the seed profile at all (e.g. against a database that's already been seeded by a previous run, or one you're managing by hand), the alternative is running scripts/week-18/002-course-public-and-source-fields.sql directly — its final UPDATE backfills the same is_public/source/insights values onto whatever course row is already titled AI Engineering From Scratch:

psql -h localhost -U ahaspace -d enlightenment -f scripts/week-18/002-course-public-and-source-fields.sql

That script only backfills an existing course row, though — it does not create the course, phases, or sections from scratch. If the database is empty, the seed profile above is the only path that produces anything to browse at all.

Data layer — courses gains 5 columns

scripts/week-18/002-course-public-and-source-fields.sql adds is_public boolean not null default false, plus four nullable columns: source_name, source_url, source_license, insights (TEXT, newline-separated — split into an array server-side by CourseService.toDto, never parsed by the frontend). Verified below with the H2 web console pointed at the real running Postgres database — the same tool, same technique Week 9's guide used, just against Postgres this time instead of the in-memory H2 database.

02

Schema — the 5 new columns, real types and nullability

Spring Boot's H2 console (enabled in application.yaml, h2.console.enabled: true) is a generic JDBC SQL client — it isn't limited to H2 databases, it can point at any JDBC URL, including the dev profile's live Postgres connection. Queried information_schema.columns directly rather than eyeballing the tree view, so the exact type and nullability of every new column is unambiguous.

is_public boolean, NO (not-nullable) confirms the migration's three-step add-nullable / backfill / constrain-after sequence completed — Postgres refuses ADD COLUMN ... NOT NULL outright on a populated table, which is exactly why the script does it in three steps instead of one.

Recreate this step
  1. With the backend running (Setup above), open http://localhost:8080/h2-console.
  2. The login form is pre-filled from application-dev.yaml's datasource: Driver Class org.postgresql.Driver, JDBC URL jdbc:postgresql://localhost:5432/enlightenment, User Name ahaspace. Fill in Password: ahaspace, click Connect.
  3. Run: 
    SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'courses'
ORDER BY ordinal_position;

New and changed endpoints

All four new routes live under /api/public/courses, mapped in a separate PublicCourseController so the "no auth required" surface stays visible in one file. Every card below is a real curl call against the running backend — real request, real response body, rendered into a card for readability (styled like a REST client, not one). A private-or-nonexistent course id resolves to the same 404 either way, by design: getPublicCourse/etc. all guard on findByIdAndIsPublicTrue, so a visitor probing course ids can never learn whether an id exists but is private, versus not existing at all.

07

Existing GET /api/courses — same path, wider DTO

No new route on CourseController — it responds at exactly the same path as every prior week. What changed is the shape of every course in the array: isPublic, sourceName, sourceUrl, sourceLicense, insights are now present on every entry (with source fields null/insights [] for a course with no attribution, as the private draft course shows). Note the wire key is exactly isPublic, not public — CourseDto pins it with @JsonProperty("isPublic") specifically because Lombok's default getter naming for a primitive boolean isPublic would otherwise serialize it as "public".

And the existing 403-when-unauthenticated behavior is completely unchanged — this route was never permitAll and still isn't:

Troubleshooting

Week 17's testing guide was never actually committed to this branch — it exists only in a git stash on main — so there is nothing to check docs/testing/week-17/ for or carry forward from it. Everything below is specific to what actually came up while building this week's guide.

Seed run does nothing / /api/public/courses returns []

Two independent causes produce the same symptom. First: the seed profile was not included alongside dev — CurriculumSeedRunner is @Profile("seed") and simply doesn't exist as a bean otherwise, no error, no log line, nothing. Second: curriculum.source-path was not passed — without a default anywhere in the YAML config, Spring fails placeholder resolution for the @Value field at startup, which surfaces as a bean-creation error mentioning curriculum.source-path could not be resolved.

Fix applied
Confirm the startup log's profile line reads The following 2 profiles are active: "dev", "seed" (not just "dev"), and that -Dspring-boot.run.arguments=--curriculum.source-path=... points at a real checkout of ai-engineering-from-scratch with a phases/ directory inside it.

Postgres role/database don't exist yet on a fresh install

Hit this directly while building this guide: Docker Desktop's daemon wasn't running, so Postgres was started via a native Homebrew install instead of this project's docker-compose.yml — which meant the ahaspace role and enlightenment database the compose file would normally create automatically didn't exist. Connecting with psql -U ahaspace -d enlightenment failed with FATAL: role "ahaspace" does not exist.

Fix applied 
psql -h localhost -p 5432 -d postgres -c "CREATE ROLE ahaspace WITH LOGIN PASSWORD 'ahaspace';"
psql -h localhost -p 5432 -d postgres -c "CREATE DATABASE enlightenment OWNER ahaspace;"
Using docker compose up -d from a running Docker daemon avoids this entirely — the Postgres image's POSTGRES_DB/POSTGRES_USER/POSTGRES_PASSWORD env vars in docker-compose.yml create both automatically on first start.

Confusing a private course's 404 for a bug

Not a bug: this is the exact, deliberate behavior decisions.md calls for. GET /api/public/courses/2 (the private draft course) and GET /api/public/courses/999 (an id that doesn't exist at all) return byte-identical 404 bodies. There is no way, from the public API alone, to tell "this course exists but is private" apart from "this course doesn't exist" — that's the entire point of guarding every public method on findByIdAndIsPublicTrue rather than checking existence and visibility separately.

Fix applied
Not applicable — this is expected behavior, verified in the Endpoints section above.
