Week 11 — Structured logging

Setup

Only the backend needs to run. Nothing this week touches AhaSpaceUI or the database schema, so there's no frontend step and no Data layer group in this guide — see Troubleshooting below if you're used to those being here from prior weeks.

Start the backend
  1. Kill any backend still holding port 8080 from a previous run. Safe to run even if nothing is listening: 
    lsof -ti:8080 | xargs kill -9 2>/dev/null; true
  2. Make sure the Postgres container is up (idempotent — safe whether it's already running or not): 
    cd AhaSpace
docker compose up -d
docker exec ahaspace-postgres pg_isready -U ahaspace -d enlightenment
  3. Run the app with the dev profile: 
    ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
    Unlike some earlier weeks' guides, no DB_URL/DB_USERNAME/DB_PASSWORD environment variables are needed — this repo's application-dev.yaml now has the Postgres connection values written in directly rather than as ${DB_URL}-style placeholders, so there's nothing to export.
  4. Wait for SERVER IS LIVE on http://localhost:8080!. Before that line, confirm the new pattern is actually attached — every line since the banner should already look like this, not Spring Boot's plain default format:

Auth-gated flow — the four log levels, one real request at a time

This is the actual "every new/changed endpoint" verification for this week. /api/auth/register, /api/auth/login, and /api/courses are all pre-existing and completely unchanged in behavior — same status codes, same response bodies as before this week's PR. What's new is that each call now leaves a trace. Every command below was run for real against a live local server; every terminal block is the actual matching output, not a hand-written example.

02

Register — DEBUG, anonymous

RequestLoggingInterceptor.preHandle fires right after Spring MVC resolves AuthController.register as the handler, before the method body runs. /api/auth/register is permitAll() in SecurityConfig, so JwtFilter never puts anything into MDC for this request — the pattern's %X{username:-anonymous} default is what fills in anonymous.

terminal — request + matching console line
$ curl -s -X POST localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"week11_tester","password":"testpass123"}'
{"message":"User registered successfully"}

03

Log in and capture the JWT — DEBUG, still anonymous

/api/auth/login is also permitAll(). Logging in successfully authenticates the response (it hands back a token) but the login request itself arrives with no Authorization header, so JwtFilter has nothing to validate and MDC stays unset — hence anonymous again here, even though the call succeeds and returns a usable token.

04

An authenticated call — DEBUG, real username

Now send $TOKEN as a Bearer header on a real request. JwtFilter validates it, puts username into MDC right after populating SecurityContextHolder, and every log line for the rest of this request — including the interceptor's — renders it. Nothing was passed into log.debug(...) to make this happen; the interceptor's code is identical to step 02/03's, only the MDC state differs going in.

terminal — request + matching console line
$ curl -s -o /dev/null -w "HTTP %{http_code}\n" localhost:8080/api/courses \
  -H "Authorization: Bearer $TOKEN"
HTTP 200

Recreate this step

05

Malformed Authorization header — WARN

Before this week, JwtFilter's catch block was catch (Exception ignored) — a bad token failed silently and the request just continued unauthenticated, indistinguishable in the logs from a request that never sent a token at all. Now it logs at WARN with the method, URI, and exception message (no token value, no secret). Note there's no matching DEBUG line from RequestLoggingInterceptor for this one: a malformed token means no authentication gets set, SecurityConfig's anyRequest().authenticated() rejects the request with 403 inside the Spring Security filter chain, and it never reaches DispatcherServlet/the interceptor at all. The WARN line is the only trace this request leaves.

terminal — request + matching console line
$ curl -s -o /dev/null -w "HTTP %{http_code}\n" localhost:8080/api/courses \
  -H "Authorization: Bearer this.is.not.a.valid.jwt"
HTTP 403

2026-07-19 18:41:51.746 WARN  [user=anonymous] c.k.enlightenment.filter.JwtFilter - JWT validation failed for GET /api/courses: Invalid compact JWT string: Compact JWSs must contain exactly 2 period characters, and compact JWEs must contain exactly 4.  Found: 5
Recreate this step 
curl -s -o /dev/null -w "HTTP %{http_code}\n" localhost:8080/api/courses \
  -H "Authorization: Bearer this.is.not.a.valid.jwt"

Any string that isn't a real 3-part JWT works — an expired real token would hit the same catch block with a different exception message (ExpiredJwtException instead of a malformed-compact-string error), same WARN outcome.

08

Course that doesn't exist — ERROR (404), and MDC survives into the handler

CourseService.getSectionsForCourse throws ResponseStatusException(NOT_FOUND, "Course not found"); GlobalExceptionHandler.handleResponseStatus logs the resolved status and message, then returns the same 404 body as before. This request is authenticated (uses $TOKEN from step 03), so — unlike step 05's rejected request — it reaches the controller and its DEBUG line, and the ERROR line that follows still carries [user=week11_tester]. MDC is set once per request by JwtFilter and stays attached through every subsequent log call on that thread, including ones several layers deeper in a @RestControllerAdvice — not just the controller method itself.

terminal — request + matching console lines
$ curl -s -X GET localhost:8080/api/courses/9999/sections \
  -H "Authorization: Bearer $TOKEN"
{"error":"Course not found"}

2026-07-19 18:42:03.119 DEBUG [user=week11_tester] c.k.e.i.RequestLoggingInterceptor - API request GET /api/courses/9999/sections -> called getSections
2026-07-19 18:42:03.129 ERROR [user=week11_tester] c.k.e.e.GlobalExceptionHandler - Response status exception: 404 - Course not found
Recreate this step 
curl -s -X GET localhost:8080/api/courses/9999/sections \
  -H "Authorization: Bearer $TOKEN"

Any course id that doesn't exist in your local database works — the table is empty by default since there's no seed data and no create-endpoint (same as prior weeks), so almost any id will 404 this way without extra setup.

Common errors and suggested solutions

One carries forward from Week 10's guide because the underlying mechanism didn't change; the rest are new to this week.

"Port 8080 was already in use" on startup (carried forward)

Spring Boot's APPLICATION FAILED TO START banner. Cause: a previous run of this same app is still alive and holding the port.

Fix applied
  1. Find the process: 
    lsof -nP -iTCP:8080 -sTCP:LISTEN
  2. Confirm it's the stale app: 
    ps -p <PID> -o pid,ppid,etime,command
  3. Stop it: 
    kill -15 <PID>
    then 
    kill -9 <PID>
    if it's still listed a few seconds later.

New: "I don't see DEBUG lines at all"

Two independent things both have to be true for a DEBUG line to appear, and it's easy to satisfy only one. First, the root logger in logback-spring.xml is deliberately set to INFO (so third-party libraries don't flood the console at DEBUG) — but there's a package-specific override, <logger name="com.kkalchake.enlightenment" level="DEBUG"/>, that raises it back up just for this app's own code. Second, logback-spring.xml has to actually be picked up: it lives at src/main/resources/logback-spring.xml and Spring Boot auto-detects that filename with zero explicit wiring — if you ever rename it to plain logback.xml alongside it or otherwise end up with two logging config files, Spring Boot's usual resolution order applies and can pick the wrong one.

How to check
  1. Confirm the file is where Spring Boot expects it: 
    ls src/main/resources/logback-spring.xml
  2. Watch for the interceptor's own logger name specifically while replaying step 02 above: 
    tail -f <wherever mvnw's stdout is going> | grep RequestLoggingInterceptor

New: no DB_URL/DB_USERNAME/DB_PASSWORD exports needed anymore

Earlier weeks' guides exported these three as env vars inline with mvn spring-boot:run because application-dev.yaml used to read them via ${DB_URL}-style placeholders, and exporting on a separate shell line before mvn silently failed to reach the subprocess. That's no longer the shape of this file — the Postgres connection values are written in directly. If you copy an old command with the three exports from a prior week's guide it will still work (the exports are simply unused), but they're not required and this guide's Setup section above omits them.

How to check 
grep -A4 'datasource:' src/main/resources/application-dev.yaml

If url is a literal jdbc:postgresql://... string rather than ${DB_URL}, no exports are needed.

New: step 05's request gets no DEBUG line — that's expected, not a bug

If you're checking off this guide's steps against console output and step 05 seems to be "missing" its interceptor line compared to every other step, that's correct behavior, not something to debug further. Spring Security's filter chain (which includes JwtFilter) runs before DispatcherServlet ever resolves a handler method. A request that fails authentication gets rejected with 403 inside that filter chain and never reaches RequestLoggingInterceptor.preHandle at all — the WARN line from JwtFilter is the complete trace for that request, by design.

Where this is enforced
See SecurityConfig.filterChain's .anyRequest().authenticated() and the filter ordering set by .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class) — both predate this week's changes and were not touched by it.
