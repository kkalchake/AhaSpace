Environment 1 — default profile (in-memory H2)

No Docker, no environment variables. This is the fastest way to validate the endpoint logic itself.

Set up this environment
  1. From the repo root: 
    cd AhaSpace
mvn spring-boot:run
  2. Wait for SERVER IS LIVE on http://localhost:8080! in the console output.
  3. That's it — the default application.yaml profile points at jdbc:h2:mem:learning_db, an in-memory database Hibernate creates fresh on every restart.
01

Schema created on startup

Connected to the running app's H2 console. The left tree shows COURSES, SECTIONS, and USER_COURSES alongside the existing CHAT_MESSAGES/CHAT_SESSIONS/USERS tables — Hibernate's ddl-auto=update generated all three new tables from the entity annotations with no manual migration.

Recreate this step
  1. With the server running (see setup above), open http://localhost:8080/h2-console in a browser.
  2. Leave Driver Class as org.h2.Driver and JDBC URL as jdbc:h2:mem:learning_db — both are pre-filled.
  3. Set User Name to sa, leave Password blank.
  4. Click Connect. The left-hand tree lists every table that exists right now.

Tear down this environment
  1. Stop the app: Ctrl+C in the terminal running mvn spring-boot:run (or the Stop button if you launched it from an IDE).
  2. That's the entire teardown — H2 here is jdbc:h2:mem:learning_db, an in-memory database that only exists inside this app's own JVM process. The instant the JVM exits, the database (schema, rows, everything from steps 01–06) is gone with it. There's no separate database process to stop, no container, nothing left holding a connection open.
  3. Optional housekeeping: close the H2 console browser tab (its connection dies with the app anyway) and clear the shell variable from step 08: 
    unset TOKEN
  4. If Ctrl+C doesn't actually kill the process and a later run fails with "Port 8080 was already in use," see the Common errors and suggested solutions section below for how to find and stop the leftover process.
Environment 2 — dev profile (real Postgres)

Same 12 checks, run again against the actual Postgres container used for the dev profile — this is what confirms the schema and queries behave identically outside of H2, including real column types.

Set up this environment
  1. Start the Postgres container (config committed at AhaSpace/docker-compose.yml — from the repo root): 
    docker compose up -d
    Safe to run no matter what state the container is already in — missing, stopped, or already running — it won't error or create a duplicate. Do not use docker run --name ahaspace-postgres ... here: that command always tries to create a brand-new container, so it fails with a name conflict if one already exists, and fails again with a port conflict if you rename it to dodge that — docker compose up -d exists specifically to avoid both.
  2. Confirm it's actually accepting connections before starting the app (it can take a second or two after docker compose up -d): 
    docker exec ahaspace-postgres pg_isready -U ahaspace -d enlightenment
  3. Run the app with the dev profile, exporting the three variables it needs in the same command — this is the step that broke earlier when the variables weren't actually reaching the mvn process: 
    cd AhaSpace
DB_URL=jdbc:postgresql://localhost:5432/enlightenment \
DB_USERNAME=ahaspace \
DB_PASSWORD=ahaspace \
mvn spring-boot:run -Dspring-boot.run.profiles=dev
  4. Wait for SERVER IS LIVE on http://localhost:8080!. In the startup log you should also see Hibernate's real DDL, e.g. Hibernate: create table courses (id bigserial not null, ...) — if you instead see a driver error mentioning ${DB_URL} literally, the export didn't take effect; re-run as one single command exactly as above rather than exporting the variables in a separate line first.

Tear down this environment
  1. Stop the app first: Ctrl+C in the terminal running mvn spring-boot:run (or the Stop button in an IDE). This is the step that actually matters here — it lets HikariCP (the connection pool the app uses) close every open connection to Postgres cleanly. Killing the terminal window itself instead (rather than the process inside it) can skip that, leaving connections sitting in Postgres until its own timeout reaps them.
  2. Optional verification, with the container still running: confirm nothing is still holding a connection open against enlightenment: 
    docker exec ahaspace-postgres psql -U ahaspace -d enlightenment -c "SELECT pid, state, query FROM pg_stat_activity WHERE datname = 'enlightenment';"
    Should return no rows (or just this psql command's own session) once the app is actually stopped.
  3. Decide what to do with the container itself:
    • Testing again soon? Leave it running — docker compose up -d is safe to re-run any time, so there's no cost to leaving the container up between sessions.
    • Done for now and want to free the port/CPU, but keep your data (courses/sections/users you inserted): 
      docker compose down
    • Want to wipe the database and start from empty next time: add -v to also delete the named volume: 
      docker compose down -v
      This is destructive — it deletes ahaspace-postgres-data, which is the only thing that makes your rows survive a container restart. Not the default; only do this deliberately.
  4. Clear the shell variable from step 08: 
    unset TOKEN
Common errors and suggested solutions

Two errors interns are likely to hit when getting this backend running locally, with the exact diagnosis and fix applied each time.

"Port 8080 was already in use" on startup

Spring Boot's APPLICATION FAILED TO START banner, with Description: Web server failed to start. Port 8080 was already in use. Cause: a previous run of this same app (commonly an IDE "Run" that was stopped but whose JVM process didn't actually terminate) is still alive and holding the port, so the new run can't bind to it.

Fix applied
  1. Find whatever process is listening on 8080: 
    lsof -nP -iTCP:8080 -sTCP:LISTEN
    This returns a PID (and confirms it's a java process, not something unrelated using the same port).
  2. Confirm it's the stale app instance before killing anything: 
    ps -p <PID> -o pid,ppid,etime,command
    Look for EnlightenmentApplication in the command line and an ELAPSED time that predates the run you just tried to start.
  3. Stop it gracefully first (lets the JVM close DB connections, etc.): 
    kill -15 <PID>
  4. Re-check with lsof; if the process is still listed after a few seconds, force it: 
    kill -9 <PID>
  5. Re-run the app — port 8080 is free.

Postgres dev profile: driver error mentioning ${DB_URL} literally

Full error: Driver org.postgresql.Driver claims to not accept jdbcUrl, ${DB_URL}. Cause: spring.datasource.url/username/password in application-dev.yaml are bound through @ConfigurationProperties (DataSourceProperties), which does not fail at bind time on an unresolved ${...} placeholder — it leaves the literal string in place, and the failure only surfaces later when Hikari/the driver tries to use it. Made worse by three onboarding gaps: application-dev.yaml is git-ignored (it also holds a real secret, the Gemini API key) so a fresh clone has no copy and no record of what keys it needs; the matching Postgres container was a manually-run, undocumented docker run; and the README still described H2 in-memory as the database.

Fix applied
  1. Committed docker-compose.yml at the AhaSpace/ repo root defining one postgres:16 service — container name ahaspace-postgres, POSTGRES_DB=enlightenment, POSTGRES_USER=ahaspace, POSTGRES_PASSWORD=ahaspace, port 5432:5432 — so this container config is now the single source of truth for the DB credentials, instead of independently-typed prose.
  2. Committed src/main/resources/application-dev.yaml.example with real working defaults for DB_URL, DB_USERNAME, DB_PASSWORD (matching the compose file above) and a placeholder for gemini.api.key. The real application-dev.yaml stays git-ignored — DB connection values for a fixed local dev container aren't secrets, only the Gemini key is.
  3. Updated the README's "Getting Started" section: replaced Database: H2 (in-memory) with Postgres, and added the actual onboarding steps: 
    docker compose up -d
cp src/main/resources/application-dev.yaml.example src/main/resources/application-dev.yaml
# then fill in your own gemini.api.key inside that copied file
  4. Run with the dev profile, exporting all three DB variables in the same command as mvn — this is the step that broke earlier when the variables were exported on a separate line first and never reached the mvn subprocess: 
    DB_URL=jdbc:postgresql://localhost:5432/enlightenment \
DB_USERNAME=ahaspace \
DB_PASSWORD=ahaspace \
mvn spring-boot:run -Dspring-boot.run.profiles=dev
  5. Confirms the fix: if you now see Hibernate's real DDL (Hibernate: create table courses (id bigserial not null, ...)) instead of the ${DB_URL} driver error, the placeholder resolved correctly.
