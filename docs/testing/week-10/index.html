Setup

This week touches both repositories. The backend needs the same Postgres container Week 9 introduced; the frontend needs three new npm packages for Markdown/LaTeX rendering that are already committed to package.json.

Start the backend
  1. Kill any backend still holding port 8080 from a previous run — otherwise mvn spring-boot:run below fails with APPLICATION FAILED TO START (see Troubleshooting). Safe to run even if nothing is listening: 
    lsof -ti:8080 | xargs kill -9 2>/dev/null; true
  2. Make sure the Postgres container is up (idempotent — safe whether it's already running or not): 
    cd AhaSpace
docker compose up -d
docker exec ahaspace-postgres pg_isready -U ahaspace -d enlightenment
  3. Run the app with the dev profile, exporting the DB variables in the same command as mvn (see Week 9's troubleshooting notes below for why this matters): 
    DB_URL=jdbc:postgresql://localhost:5432/enlightenment \
DB_USERNAME=ahaspace \
DB_PASSWORD=ahaspace \
mvn spring-boot:run -Dspring-boot.run.profiles=dev
  4. Wait for SERVER IS LIVE on http://localhost:8080!. In the startup log you should also see Hibernate create the two new tables: 
    Hibernate: create table section_chat_messages (id bigserial not null, content TEXT not null, created_at timestamp(6) not null, model varchar(255), role varchar(255) not null, session_id bigint not null, primary key (id))
Hibernate: create table section_chat_sessions (id bigserial not null, created_at timestamp(6) not null, title varchar(255) not null, section_id bigint not null, user_id bigint not null, primary key (id))
    This is ddl-auto=update at work again — same mechanism Week 9's courses/sections tables came from. SectionChatSession/SectionChatMessage are new JPA entities that mirror ChatSession/ChatMessage field-for-field (per decisions.md), so Hibernate generates their tables the same way, with two extra foreign keys this time: section_chat_sessions.section_id → sections.id and .user_id → users.id.
Start the frontend
  1. From the frontend repo root: 
    cd AhaSpaceUI
npm install
npm run dev
  2. npm install pulls in the four packages this week added to package.json: react-markdown, remark-math, rehype-katex, katex. If these were already installed by the implementation phase, this is a no-op.
  3. Vite prints Local: http://localhost:3000/ — not the Vite default of 5173. This project's vite.config.js pins server.port: 3000 deliberately, because the backend's SecurityConfig CORS policy only allows http://localhost:3000 as an origin. If you ever see CORS errors in the browser console, the first thing to check is whether the frontend actually came up on 3000.

06

Insert two Sections

Both reference the Calculus Basics course by looking its id up with a subquery instead of a hardcoded number — this is what step 05 flagged: whatever numeric id that course actually got, this INSERT finds it correctly rather than assuming 2. (A hardcoded 2 is what caused a foreign-key violation in an earlier version of this guide when the course landed at id 1 instead.) The second section's content deliberately contains a block-level LaTeX expression ($$f'(x) = nx^{n-1}$$) and an inline one ($f(x) = x^2$) — this is the content step 22 later proves actually renders as real math in the browser, not literal dollar signs.

Recreate this step 
INSERT INTO sections (content, course_id) VALUES
  ('# Introduction to Calculus

Calculus studies **rates of change** and **accumulation** of quantities. The two foundational operations are:

- Differentiation
- Integration

We start with differentiation.', (SELECT id FROM courses WHERE title = 'Calculus Basics'));

INSERT INTO sections (content, course_id) VALUES
  ('# The Power Rule

For a function $f(x) = x^n$, the derivative is given by:

$$f''(x) = nx^{n-1}$$

For example, if $f(x) = x^2$, then $f''(x) = 2x$. This rule extends to any real exponent $n$.', (SELECT id FROM courses WHERE title = 'Calculus Basics'));

Note the doubled '' inside the SQL string literal — that's SQL's own escape for a single quote character, not a typo. It's what makes f'(x) show up correctly once the row is read back.

The (SELECT id FROM courses WHERE title = 'Calculus Basics') subquery runs once per INSERT and substitutes whatever id that course row actually has — this only works because title is unique in this seed data, not because of any database constraint enforcing it.

07

Verify both Sections, note their ids

Section 3 is the plain-Markdown one, section 4 is the math-heavy one, in this guide's own run — sectionId=4 is what every chat call below targets, and what step 22's browser screenshot opens. Endpoint: POST /chat

SectionChatController at /api/courses/{courseId}/sections/{sectionId}/chat — courseId is only in the URL for consistency with the frontend's route nesting, the actual lookup is keyed on sectionId alone. The try/catch ordering inside the controller is copied verbatim from the existing ChatController: a ResponseStatusException keeps its own status, an IllegalStateException (thrown by GeminiProvider when the API key is blank) becomes 500, and any other RuntimeException from the AI call becomes 400.

10

Success — new session, real Gemini answer

sessionId: null tells SectionChatService.processMessage to create a brand-new SectionChatSession rather than append to an existing one. The response's sessionTitle is the first 50 characters of the question (buildTitle, same truncation rule as the account-wide chat) plus "..." since the question ran past 50 characters. The response text is a genuine Gemini API call, not a stub — this is the actual model answering a question about the exact section content seeded in step 06.

Recreate this step 
curl -s -X POST localhost:8080/api/courses/$COURSE_ID/sections/$SECTION_ID/chat \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"message":"What is the derivative of x^2 according to the power rule?","sessionId":null}'

Needs a real gemini.api.key configured in application-dev.yaml (see Troubleshooting below) — without one this returns 500 instead.

Failure — section does not exist

404 with {"error":"Section not found"}. This is the very first thing processMessage does — sectionRepository.findById(sectionId).orElseThrow(...) — before it ever touches a session, a user lookup, or the AI provider. A bad sectionId fails fast, before any database write happens.

curl -s -X POST localhost:8080/api/courses/$COURSE_ID/sections/9999/chat \

  -d '{"message":"Does this section exist?","sessionId":null}'
Endpoint: GET /chat/sessions

Lists every session this user has on this section — the query is findByUserUsernameAndSectionIdOrderByCreatedAtDesc, filtered on both fields at once. That's the mechanism behind "multiple named chat threads per (user, section)" from decisions.md: nothing stops the same user from starting several independent conversations about one section, and nothing lets that list leak into a different section or a different user's sessions.

Success

One entry — the session step 10 just created. Only id, title, createdAt come back; the full message list is a separate call (step 14), so opening a section doesn't force-load every message in every one of its threads.

Recreate this step

13

Failure — no Authorization header

403 with an empty body. Same behavior Week 9 documented for /api/courses: this app's Spring Security config has no custom AuthenticationEntryPoint, so the default unauthenticated response is 403, not 401. SecurityConfig's anyRequest().authenticated() covers these new nested /api/courses/** paths automatically — no security config change was needed for this feature.

Recreate this step 
curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/api/courses/$COURSE_ID/sections/$SECTION_ID/chat/sessions
Endpoint: GET /chat/sessions/{sessionId}

Returns one session's full message history. Three checks happen in order before any data comes back: the session must exist, the caller must own it, and the session must actually belong to the sectionId in the URL (guards against reusing a session id that's valid but for a different section). This step exercises the ownership check specifically.

17

section_chat_messages — the content column is the tell

Row 1's content is exactly "What is the derivative of x^2 according to the power rule?" — the raw question, character for character. It is not "Section content:\n# The Power Rule...\n\nQuestion: What is the derivative...", which is what SectionChatService actually sent to Gemini. That augmented string is built fresh inside processMessage, passed straight to aiProvider.chat(prompt), and never saved anywhere — only the pre-augmentation question and the model's answer get written to the table. This is why re-opening an old thread later doesn't re-send the whole section content to Gemini again on every render; it only happens once, at the moment a question is actually asked.

Recreate this step 
SELECT id, session_id, role, content, model FROM section_chat_messages ORDER BY id;

Common errors and suggested solutions

Two of these carry forward from Week 9's guide because nothing about the underlying mechanism changed; two are new to this week.

"Port 8080 was already in use" on startup (carried forward from Week 9)

Spring Boot's APPLICATION FAILED TO START banner. Cause: a previous run of this same app is still alive and holding the port.

Fix applied
  1. Find the process: 
    lsof -nP -iTCP:8080 -sTCP:LISTEN
  2. Confirm it's the stale app: 
    ps -p <PID> -o pid,ppid,etime,command
  3. Stop it: 
    kill -15 <PID>
    then 
    kill -9 <PID>
    if it's still listed a few seconds later.

Postgres dev profile: driver error mentioning ${DB_URL} literally (carried forward from Week 9)

Happens if the three DB_* variables are exported on a separate shell line before running mvn, instead of inline on the same command — the export doesn't reach the mvn subprocess, so application-dev.yaml's ${DB_URL} placeholder is never resolved.

Fix applied 
DB_URL=jdbc:postgresql://localhost:5432/enlightenment \
DB_USERNAME=ahaspace \
DB_PASSWORD=ahaspace \
mvn spring-boot:run -Dspring-boot.run.profiles=dev

All three variables and the mvn invocation on one logical command, exactly as shown in Setup above.

New: Gemini returns 503 "high demand" mid-session

Hit while capturing screenshots for this guide: two consecutive real calls to gemini-2.5-flash-lite failed with 503 Service Unavailable, logged by GeminiProvider as "This model is currently experiencing high demand. Spikes in demand are usually temporary. Please try again later." This is Google's infrastructure, not application code — SectionChatController's catch-all RuntimeException → 400 "Failed to get AI response" path handled it correctly (same path a genuinely bad request would hit), it just isn't the response a user actually wants to see for a transient upstream outage.

What actually resolved it
  1. Waited roughly 8 seconds and retried the same request — five consecutive retries all came back 200.
  2. No code change was needed to reproduce a working demo; this is documented here so it isn't mistaken for an application bug if you hit it while working through this guide yourself. If it becomes a recurring problem, retry/backoff logic inside GeminiProvider would be the place to add it — out of scope for this week's decisions.md.

New: chat endpoints 404 until a Course + Section exist

The section-scoped chat endpoints have no meaning without a real Section row to attach to — there's no seed data shipped with the app, and no create-endpoint for courses/sections (by design, same as Week 9). Trying to exercise steps 10–17 before doing the Data Layer steps above just produces the same 404 as step 11's deliberate failure case, which can be confusing if you don't yet know that's expected.

Fix applied
Do the Data layer steps (04–07) first, in order, before touching any /chat endpoint. That's why this guide is sequenced the way it is rather than jumping straight to the new endpoints.
